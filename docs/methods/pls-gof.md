# 適合度指數 GoF（Goodness-of-Fit index，Tenenhaus et al. 2005）

> 方法代號 `pls_gof`｜基準組 `reference.json → pls_gof`（3 欄）｜溯源 tier **A** / verified
> 最後更新：2026-07-26（階段 A）

---

## 1. 這個方法在回答什麼問題

GoF 想用**一個數字**同時概括「測量模型有多好」與「結構模型解釋力有多強」：
取兩者代表量的幾何平均——平均 communality（測量）× 平均 $R^2$（結構）。

## 2. 什麼時候該用、什麼時候不該用

★ **先講最重要的一句：這個指標不建議用作適配指標。**

Henseler & Sarstedt（2013）以模擬證明 GoF **無法區分有效模型與無效模型**——
它沒有虛無分布、沒有拒絕域，一個結構完全錯誤的模型只要 loading 高、$R^2$ 不低，
GoF 照樣漂亮。SmartPLS 官方文件也明載不建議使用。本工具的 UI 註記已寫明這一點
（`zh-TW.js` 的 `pls.result.fitNote` 末句：「官方文件明載**不建議**作為適配指標，僅供舊文獻對照」）。

**唯一合理的用途**：與**既有文獻**對照。2005–2015 年間的 PLS 論文常報 GoF，
審稿人或指導教授要求「補上 GoF」時，本工具給得出來，並附上不建議使用的說明。

**不該用**

- 作為模型適配的證據（改用 SRMR，見 `pls-fit.md`；或 PLSpredict，見 `pls-predict.md`）
- 作為模型選擇的判準（改用 IT 準則，見 `pls-itcriteria.md`）
- 跨資料集比較

**常見誤用**：把「GoF = 0.36 以上為 large」當成適配門檻。那組門檻（.10/.25/.36）出自
Wetzels 等人（2009）的**經驗建議**，不是抽樣分布導出的臨界值，且該建議本身已被上述模擬研究質疑。
本工具**刻意不提供 GoF 的燈號**，只給數字。

## 3. 公式與定義

$$\text{GoF}=\sqrt{\overline{\text{communality}}\times\overline{R^2}}$$

其中

$$\overline{\text{communality}}=\operatorname{mean}\left\{\lambda_h^2\ :\ h\in B_j,\ \text{$j$ 為反映型且 }k_j\ge2\right\}$$

$$\overline{R^2}=\operatorname{mean}\left\{R^2_j\ :\ j\ \text{為內生構念}\right\}$$

→ `src/lib/stats/pls.js:1905–1920`（communality 蒐集 `1855–1859`、兩個平均 `1861–1862`、開根號 `1863`）

### 3.1 兩個納入範圍的慣例（本工具的選擇）

| 決定點 | 本工具 | 說明 |
|---|---|---|
| communality 的納入範圍 | **只取反映型且 $k\ge2$ 的區塊**（形成型與單指標構念排除） | 對齊 plspm 的 `goodness_of_fit()`。單指標構念的 $\lambda=1$，納入會把平均往上拉 |
| $R^2$ 的納入範圍 | **全部內生構念** | 不加權（不依指標數或前置數加權） |
| communality 的定義 | 逐**指標** $\lambda^2$ 後取平均 | 另一種寫法是先算每個構念的平均 $\lambda^2$ 再對構念取平均——**構念指標數不等時兩者不同**（見第 6 節） |

### 3.2 不計算的情形

| 情形 | 行為 |
|---|---|
| 沒有任何內生構念 | `gof = null` |
| 沒有任何反映型多指標區塊（communality 集合為空） | `gof = null` |
| $\overline{\text{communality}}\le0$ 或 $\overline{R^2}\le0$ | `gof = null`（避免開負根號） |
| 多階段模型（調節／高階構念） | 不計算（與 model fit 同一個 `skipFit` 旗標） |

→ `pls.js:1906`（`skipFit` 與內生構念檢查）、`1860`、`1863`；UI 只在 `Number.isFinite(gof)` 時顯示該列（`Result.jsx:577`）

## 4. 假設前提與本工具的檢核方式

| 前提 | 本工具怎麼檢核 | 違反時的行為 | 位置 |
|---|---|---|---|
| 至少一個內生構念 | `sm.structural.length > 0` | 不輸出 GoF 列 | `pls.js:1906` |
| 至少一個反映型多指標構念 | communality 集合非空 | 不輸出 GoF 列 | `pls.js:1910` |
| 兩個平均皆為正 | 明確檢查 | 不輸出 GoF 列 | `pls.js:1915` |
| **GoF 有統計意義** | ✗ **無法檢核** | 以 UI 註記聲明不建議使用 | `zh-TW.js` 的 `fitNote` |

★ 最後一列不是玩笑：這個指標的問題不在實作，而在**它本身沒有推論基礎**。
工具能做的只有「算對 ＋ 說清楚別拿它當適配證據」。

**已知的慣例差異**

1. **communality 的兩種平均方式**（§3.1 第三列）：本工具「逐指標 $\lambda^2$ 取平均」，
   與 plspm 一致。若改成「先對構念平均、再對構念取平均」，在構念指標數不等時數值不同。
   本資料集 M4 的三個反映型區塊都是 3 個指標（等寬），**兩種算法在此恰好同值**——
   ⇒ **這個慣例差異沒有被基準組覆蓋**，見下方「尚未驗證」第 2 點。
2. **單指標構念排除**：與 plspm 一致；未知 SmartPLS 舊版是否相同（已移除該指標，無從對照）。
3. **$R^2$ 不加權**：所有內生構念等權。未查是否有文獻要求加權。

### ★ 尚未驗證的部分

1. **Tenenhaus et al. (2005) 原文未取得**，方程式編號未核對。本組敢標 tier A，
   是因為**數值直接對得上 plspm 的 `goodness_of_fit()`**，不是因為公式對過原文。
2. **★ communality 平均方式的慣例差異未被基準覆蓋。** M4 的三個反映型區塊等寬（各 3 指標），
   兩種算法同值，所以現有 fixture **抓不到**這個口徑被改動。這與 `pls_plsc_pw` 的成因同類
   （組合／情境未被基準覆蓋），只是後果輕微得多（GoF 本身不建議使用）。
   建議：若日後 GoF 仍保留，補一組**指標數不等**的 fixture。
3. **GoF 的抽樣分布未知，本工具不提供任何推論。** 這是方法本身的性質，不是實作缺口。
4. **邊界條件僅部分測試**：`gof = null` 的四種情形（§3.2）中，只有「多階段模型不計算」
   有測試覆蓋（`pls.test.js` 的 W4 相關測試）；其餘三種**無測試**。
