> 方法代號 `pls_mod_pi`｜基準組 `reference.json → pls_mod_pi`（4 欄）｜溯源 tier **B** / verified
> 最後更新：2026-07-26（階段 A / A2）

## 1. 這個方法在回答什麼問題

與 two-stage 法（見 `pls-moderation-twostage.md`）回答同一個問題——**X 對 Y 的影響會不會隨 W 而變**——
但走另一條路：不先算構念分數，而是**在指標層直接造出交互構念**。

做法：把 X 的每個指標與 W 的每個指標**兩兩相乘**，$k_a\times k_b$ 個乘積當成交互構念的指標，
然後整個模型（含交互構念）**一次估計完**。

這是 PLS-SEM 最早的調節作法，歷史上被引用最多。

## 2. 什麼時候該用、什麼時候不該用

**該用**

- 兩個**反映型**構念的調節，且指標數不多
- 要與採用此法的既有文獻對照
- 想保留「交互構念也有測量模型」的形式

**不該用**

- **因子含形成型構念**：本工具**硬擋**（`pls.js:374`）
- **二次效果或三向以上**：本工具**硬擋**（只支援兩個**相異**構念，`pls.js:367`；實測確認）
- **指標數多**：$k_a\times k_b$ 個乘積指標。3×3 已是 9 個；5×5 就是 25 個
- **指標間共線性高**：乘積指標彼此高度相關，交互構念的權重會不穩

**★ 常見誤用（本節最重要）**

1. **拿一般門檻判交互構念的信效度。** 實測本工具的示範模型，交互構念 F1×C 的
   **AVE = 0.286、rho_A = 0.419**——若照 AVE ≥ .50、信度 ≥ .70 判讀，它「不合格」。
   但乘積指標本來就不是同一個共同因素的展現，**這些門檻在此不適用**。
   本工具因此把交互構念在信效度表中**單列、不判紅綠**（見 §3.4）。
2. **拿本法的係數與 two-stage 的係數直接比較。** 兩者量尺不同（§3.3）。
3. **忘記乘積指標的 loading 有正有負是正常的。** 見 §3.4。

## 3. 公式與定義

### 3.1 乘積指標的建構

設 $X$ 的指標為 $\{x_1,\dots,x_{k_a}\}$、$W$ 的指標為 $\{w_1,\dots,w_{k_b}\}$，
先各自 z-score，再取全配對乘積：

$$p_{ab}=z(x_a)\cdot z(w_b),\qquad a=1,\dots,k_a;\ b=1,\dots,k_b$$

這 $k_a k_b$ 個乘積欄成為交互構念 $I$ 的指標（反映型 Mode A），
隨後與其他指標一起進入引擎（引擎內部會再逐欄標準化）。

→ `src/lib/stats/pls.js:1669–1717`（z-score 快取 `1644–1650`、全配對乘積 `1655–1671`、掛成構念 `1672`）

★ **單一估計**：與 two-stage 不同，本法**沒有兩個階段**——交互構念與其他構念在同一次
Lohmöller 迭代中估計，因此 model fit **照常計算**（two-stage 則不報）。

### 3.2 主效果與結構模型

主效果路徑的自動補齊與 two-stage 相同（見 `pls-moderation-twostage.md` §3.1）。
實測：宣告 `F1×C→Y` 時 `autoAddedPaths` 回傳 `[{F1→Y}, {C→Y}]`。

結構模型即一般的構念相關矩陣 OLS（見 `pls-basic.md` §3.5），交互構念作為一個普通的前置構念。

### 3.3 ★ 係數量尺（與 two-stage 不同）

本法的交互項係數以**標準化量尺**回報（`coefStd` 與 `coef` 相同，`applyInteractionRescale`
因 `sdProduct = null` 而不作用，`pls.js:1703`、`1929`）。

這是**對齊 seminr 的 `product_indicator`**，不是 SmartPLS 的慣例。

★ **已知的量尺換算**（2026-07-13 R 抽驗記錄）：seminr 報未標準化係數 0.194690，
其交互構念分數 $\operatorname{sd}=1.001905$；$0.194690\div1.001905=0.194320$ ＝本工具的值。
**配適完全相同，只是量尺表述不同。**

### 3.4 ★ 交互構念的測量指標怎麼讀（2026-07-26 新增處置）

實測本工具示範模型的交互構念 F1×C（9 個乘積指標）：

```
loading: 0.050  0.233  −0.047  0.766  0.767  0.835  0.429  0.579  0.354
α = 0.907   rho_A = 0.419   CR = 0.710   AVE = 0.286
```

兩件事都是**乘積指標的正常性質**，不是資料錯誤：

1. **loading 正負混雜**——兩個標準化變數的乘積，其與構念分數的相關本來就可正可負。
   ★ A1 的 R4 曾對此誤報「反向題未反向計分」警告，2026-07-26 已排除交互構念（見 §8 R13）。
2. **AVE 與信度偏低**——乘積指標不是同一個共同因素的展現。
   ★ 2026-07-26 起信效度表對交互構念**單列並標註「（交互構念）」、不判紅綠燈**（見 §8 R14）。

## 4. 假設前提與本工具的檢核方式

| 前提 | 本工具怎麼檢核 | 違反時的行為 | 位置 |
|---|---|---|---|
| 恰兩個**相異**構念 | 驗證器 | **硬擋**「只支援兩個相異構念（二次效果與三向以上請用 two-stage）」（實測確認） | `pls.js:367` |
| 兩個因子皆為反映型 | 驗證器 | **硬擋**，指名形成型的那一個 | `pls.js:374` |
| 指標非零變異 | 建乘積前逐欄檢查 | **硬擋** `zero-variance`，指名指標 | `pls.js:1687–1689` |
| 多個交互項 method 一致 | 驗證器 | **硬擋**（實測確認） | `pls.js:383` |
| 不與 PLSc 併用 | 建模階段 | **硬擋**（實測確認） | `pls.js:1354–1359` |
| **乘積指標的共線性** | ✗ **不檢核** | 無警告——交互構念是反映型，不算外部 VIF | — |
| 交互構念的信效度門檻 | 不適用 | 單列不判燈號＋標註（2026-07-26 起） | `Result.jsx` 的 `ReliabilityTable` |

### ★ R13（L2，已修）A1 的「負荷量正負混雜」警告在交互構念上誤報

這是**我在 A1 自己引入的假陽性**，記錄於此以示可稽核。

A1 的紅隊 R4 為了抓「反向題未反向計分」，加了一條警告：反映型區塊內同時出現正負 loading 時提醒。
但**交互構念的乘積指標本來就會正負混雜**——實測 F1×C 的 9 個 loading 中有一個為 −0.047，
於是 product-indicator 與 orthogonalizing 兩法**每次都會跳出一則錯誤的診斷**：
「常見原因為反向題未事先反向計分」。

**處置（依 §6.4 為 L2，當場修）**：`reportFromStage` 的資料品質警訊迴圈**排除交互構念**
（`ctx.interactionLVs`，由 `runPLS` 從 `plan.ints` 帶入）。
→ `pls.js:2278`（ctx 傳入）、資料品質警訊迴圈的排除條件。
新增 3 條行為測試：兩種方法都不得誤報；**且一般構念的未反向計分仍必須被抓到**
（防止修過頭把 R4 整條廢掉）。

### ★ R14（L2，已修）交互構念在信效度表亮紅燈

**實測**：product-indicator 的 F1×C 得到 AVE = 0.286、rho_A = 0.419，
在信效度表中列首燈號為紅、兩欄數字為紅。

但乘積指標的 AVE／信度**本來就不該用 .50／.70 判**。使用者看到一整列紅色，
合理的反應是「我的交互構念測量品質不好」——那是錯的診斷。

**處置（Kevin 2026-07-26 核定：單列並加註）**：信效度表對交互構念
**照列數字（保持透明）但不判紅綠、不計入列首燈號**，並在構念名後標「（交互構念）」。
→ `Result.jsx` 的 `ReliabilityTable`（`intLvs` 判斷）；i18n 新增 `interactionTag`（中英各一）。
