# 高階構念：disjoint two-stage 法

> 方法代號 `pls_hoc_disjoint`｜基準組 `reference.json → pls_hoc_disjoint`（6 欄）｜溯源 tier **B** / verified
> ★ Becker et al. (2023) 明確建議**優先採用本法**
> 最後更新：2026-07-26（階段 A / A2）

---

## 1. 這個方法在回答什麼問題

高階構念的背景見 `pls-hoc-repeated.md` §1。本文件說明 **disjoint two-stage**：

1. **第一階段**：模型裡**沒有 HOC**。低階構念（LOC）直接承接 HOC 原本的所有結構關係，估計後取 LOC 分數
2. **第二階段**：HOC 以那些 LOC 分數為指標；**其他構念仍用原始指標**

「disjoint（互斥）」指的是第一階段的各 LOC 區塊互不重疊——與 repeated indicators
讓 HOC 與 LOC 共用指標形成對比。

## 2. 什麼時候該用、什麼時候不該用

**該用（這是現行首選）**

Becker et al. (2023) 明確建議優先用 disjoint two-stage，理由是：
**它容許在指標層跑 PLSpredict／CVPAT**——embedded 法的非階層構念在第二階段被換成單指標分數，
就失去指標層的預測評估能力。

其他優點：

- 各 LOC 的指標數不均時，偏誤比 repeated indicators 小（HOC 的權重是對 LOC 分數算的，一個 LOC 一票）
- 第一階段沒有重複掛載，指標相關矩陣正常，第一階段的量測與適配可正常解讀

**不該用／要小心**

- **需要第二階段的 model fit**：多階段模型不報 fit（`stage1` 提供第一階段量測）
- **第一階段的結構關係要合理**：LOC 直接連下游時，各 LOC 的路徑係數會被分別估計，
  若 LOC 之間高度相關會有共線問題

**常見誤用**

1. **以為三種 HOC 法的結果應該一樣。** 實測同一份資料：G→C 的係數為
   repeated **−0.348**／disjoint **−0.402**／embedded **−0.345**——差異不小。
   方法選擇要在看結果之前決定。
2. **拿第二階段 HOC 的 loading 當測量品質證據。** 那是 LOC 分數對 HOC 的負荷量，
   反映的是「這個面向在上位構念裡的份量」，不是題目的測量品質。

## 3. 公式與定義

### 3.1 第一階段：把 HOC 的結構關係轉嫁給 LOC

設 HOC $h$ 的成分為 $\text{comp}(h)$。第一階段的路徑集合由原路徑逐條改寫：

| 原路徑 | 改寫為 |
|---|---|
| $a\to b$（兩端皆非 HOC） | 原樣保留 |
| $h\to b$ | 對每個 $c\in\text{comp}(h)$：$c\to b$ |
| $a\to h$ | 對每個 $c\in\text{comp}(h)$：$a\to c$ |
| $h_1\to h_2$ | 對每組 $(c_1,c_2)$：$c_1\to c_2$（笛卡兒積） |

→ `src/lib/stats/pls.js:1527–1546`（`hocDisjointStage1`：四種情形於 `1507–1513`，去重於 `1503–1506`）

第一階段的構念清單**不含 HOC**，各 LOC 用自己的原始指標。

→ `pls.js:1599–1601`

### 3.2 第二階段

- **HOC** 的指標 = 第一階段的 LOC 分數（欄名 `{LOC}_score`）
- **其他構念**保留**原始指標**（這是 disjoint 與 embedded 的關鍵差異）

→ `pls.js:1609–1628`（HOC 組裝 `1582–1586`、非成分構念的分支 `1587–1596`；
disjoint 走 `1589–1591` 的「用原始指標」分支）

★ 使用者宣告的路徑**不變**（`pls.js:1629` 的註解：驗證器保證路徑只用 HOC 名稱、不含 LOC）。

### 3.3 符號校正

取分數時會套用 `computeFlip` 的翻轉旗標（`pls.js:1580–1587`），
確保 bootstrap 重抽時第一階段的構念方向與原始估計一致。

→ `pls.js:1566–1579`（錨定於原始估計的 loadings）

   重生不會紅燈——只有 `compare.test.js` 的 JS↔fixture 比對會抓到「JS 改了但 fixture 沒改」，
   抓不到「兩邊一起改錯」。

### R20（L1，已記錄）HOC→HOC 的路徑改寫分支未被基準覆蓋

差別是後果輕微得多——這條分支的邏輯是純粹的模型改寫（不涉及統計量），
且行為測試中有 HOC 相關的煙霧測試。
